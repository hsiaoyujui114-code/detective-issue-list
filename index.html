§3問題清單（13 題）

嚴重度說明：高＝資料已經分叉或功能會壞，先修；中＝文件與現況不符、或遲早出事；低＝整潔與可維護性。用下面的按鈕篩選，或搜尋關鍵字。

ISSUE-01高資料同步rpg · city-pulse · metro

cases.json 三個倉庫已經是不同版本，metro 那份缺三個欄位

問題：同一份 50 案資料存在三個倉庫，大小已經對不起來。metro 的版本明顯較舊，少了 chapter、diy_experiment、cross_case_clue 三個欄位——玩家在哪個入口玩，看到的案件資料就不一樣。

taipei-detective-rpg … cases.json = 536,111 bytes city-pulse-detective … cases.json = 536,102 bytes（與 rpg 差 9 bytes，也需比對） taipei-metro-detective-rpg … cases.json = 437,702 bytes（缺 chapter / diy_experiment / cross_case_clue）
修復方式與驗證
  1. 逐欄位比對三份 cases.json，確認最完整的一份為準（預期是 rpg 或 city-pulse）。
  2. 把基準版複製到其他倉庫；9 bytes 的差異也要查明是什麼，不要直接忽略。
  3. 在回報中寫明基準版來源與比對結果。
驗證：三份檔案 byte 數與雜湊值一致；隨機抽 5 案檢查三欄位都存在。
ISSUE-02高資料同步rpg

rpg 的 shared-data.js 只有約 38 KB，其他倉庫是約 145 KB 的完整版

問題：共用資料檔在 rpg 倉庫是殘缺版，約只有完整版的四分之一。任何從 rpg 入口載入共用資料的功能，都可能拿到不完整的資料。

taipei-detective-rpg … shared-data.js ≈ 38 KB taipei-metro-detective-rpg / city-pulse-detective … shared-data.js ≈ 145 KB
修復方式與驗證
  1. 確認 145 KB 版是現行完整版，覆蓋 rpg 的殘缺版。
  2. 檢查 rpg 端引用 shared-data.js 的頁面，確認沒有寫死舊版才有的結構。
驗證：三個倉庫的 shared-data.js 大小與雜湊一致；rpg 的企劃書與案件頁開啟無主控台錯誤。
ISSUE-03高編號對照全部倉庫 · 企劃書

50 案全集與 10 示範案的編號對不上，同一個 CASE-03 是兩宗不同的案

問題：兩份清單用了同一套 CASE 編號，順序卻不同。只報編號、不報案名時，讀者（包括評審與協作 AI）會對到錯的案件。

50 案全集 CASE-03 = 西門町超商指紋竊案 10 示範案 CASE-03 = 淡水跳舞小人航海磚案
修復方式與驗證
  1. 製作「全集編號 ↔ 示範案編號 ↔ 案名」對照表，10 案全列。
  2. 對照表放進企劃書（見 P-03），cases.html 也加連結。
  3. 之後所有對外文件一律寫「編號＋案名」，不單寫編號。
驗證：對照表 10 列與兩份原始清單逐列核對無誤。
ISSUE-04高缺檔rpg

rpg 缺 assets/three.min.js 與 vendor/leaflet/，HTML 有引用、檔案不存在

問題：rpg 的頁面引用了 Three.js 與 Leaflet，但倉庫裡沒有這兩個檔案／目錄。引用到的頁面會載入失敗，3D 或地圖功能直接壞掉。

修復方式與驗證
  1. 從有完整檔案的倉庫複製 assets/three.min.js 與 vendor/leaflet/ 到 rpg。
  2. 若確認 rpg 根本用不到，改為移除引用——二選一，並在回報說明理由。
驗證：全站搜尋引用路徑，逐一確認檔案存在；開啟相關頁面無 404。

驗證：core 本機啟動（localhost:3001）後跑完 10 階段測試仍全過；CASE-03 對話可完整走完一輪。
ISSUE-06中設定檔rpg · city-pulse

package.json 名字寫錯：rpg 與 city-pulse 都寫成 taipei-metro-detective-rpg

問題：兩個倉庫的 package.json 名稱與 repository 欄位都複製了 metro 的，沒改成自己的。工具與協作 AI 判斷「這是哪個倉庫」時會被誤導；另外部分 lock 檔缺失或幾乎空白，依賴版本無法重現。

修復方式與驗證
  1. rpg 改為 taipei-detective-rpg、city-pulse 改為 city-pulse-detective，repository 一併改正。
  2. 重新產生並提交完整的 lock 檔。
驗證：四個倉庫的 package.json 名稱互不相同且與倉庫名一致；乾淨環境照 lock 檔可成功安裝。
ISSUE-07中文件不符全部倉庫 · 企劃書

README 寫有自動部署，但四個倉庫都沒有.github/workflows/deploy.yml

問題：GitHub Pages 實際是通的、網站打得開，但倉庫裡找不到部署設定檔，所以「到底怎麼部署的」無法從倉庫確認。文件宣稱的自動部署與倉庫現況對不起來（企劃書同樣受影響，見 P-01）。

修復方式與驗證
  1. 先確認目前 Pages 的實際部署來源（分支／資料夾）。
  2. 二選一：補上真正的 deploy.yml，或把 README 與企劃書改成實際部署方式的說明。
驗證：文件描述與倉庫設定一致；推一次小改動後 Pages 內容有更新。
ISSUE-08中架構耦合metro · core

地圖倉庫的 server.js 硬引用兄弟目錄../taipei-detective-core，單獨 clone 跑不起來

問題：偵探核心 API 要靠兩個本機服務搭配：地圖倉庫的 localhost:3000 掛 core 的 localhost:3001。但 server.js 直接假設 core 就在隔壁目錄——任何人只 clone 一個倉庫，偵探功能就啟動不了，而且錯誤訊息不會告訴他原因。

修復方式與驗證
  1. README 明寫前置條件：需同時 clone 兩個倉庫並放在同一層目錄，兩個服務都要啟動。
  2. server.js 啟動時檢查 core 目錄是否存在，缺失時印出友善錯誤訊息說明缺什麼、去哪 clone。
驗證：只 clone 地圖倉庫時，啟動會得到清楚的提示而不是不明錯誤；雙倉庫就位時功能正常。
ISSUE-09中規劃落差企劃書 · 全部倉庫

規劃寫 PixiJS＋Socket.io，實際是自寫 Canvas＋ws——只改文件，不要換引擎

問題：企劃與規劃文件宣稱的技術與實作不同：game.js 是自寫 Canvas 渲染、server.js 用的是 ws。文件自己也承認這個落差。現行實作能跑，問題只在說法。

修復方式與驗證
  1. 把文件改成兩段：「目前實作＝自寫 Canvas＋ws」與「未來若重構才考慮 PixiJS／Socket.io」。
  2. 不要真的動手換引擎——那會把能玩的遊戲弄壞，不在本清單範圍。
驗證：文件全文搜尋 PixiJS／Socket.io，只出現在「未來規劃」脈絡；遊戲試玩入口功能不變。
ISSUE-10中缺測試metro · city-pulse

§4企劃書本身的問題（P-01～P-05）

Alan 特別問的：企劃書（proposal.html，位於 taipei-detective-rpg）裡有沒有問題——有，五個，都是「企劃書說的」跟「倉庫實際現況」對不起來。修法都已寫進 §3 對應題目，這裡集中列給評審前檢查用。

    企劃書讀起來像所有功能線上就能玩，但 core 引擎需要 localhost:3000＋3001 搭配、且兩倉庫要並排 clone。修法見 ISSUE-08：企劃書的「系統架構」段落補上這項前置條件。

§5建議修復順序（由易到難）

照這個順序做，前面的都是低風險、不動玩法的修正；越後面越需要寫程式與測試。

  1. 先修同步漂移（ISSUE-01、02）

    純資料同步、不動玩法，風險最低。以最完整版本為準，把 cases.json 與 shared-data.js 在各倉庫對齊。

  2. 修 package.json 與 lock 檔（ISSUE-06）

    改回各倉庫自己的名稱與 repository，補齊 lock 檔。順手處理缺檔（ISSUE-04、05）也可以排在這一步。

  3. 做案件編號對照（ISSUE-03 ＋ P-03）

    產出對照表放進企劃書；對外文件改成「編號＋案名」；core 補 CASE-03 對話樹（ISSUE-05 後半）。

  4. 修文件說法（ISSUE-07、09、12 ＋ P-01、02、04、05）

    部署、技術棧、四倉庫關係、雙服務前置條件——全部改成與現況一致的描述。

  5. 幫地圖線加檢查腳本（ISSUE-10、11）

    把 core 的可重跑測試做法複製過來，讓下一次同步漂移在推送當下就被抓到，而不是等下次審核。

另外，ISSUE-13（Instinct 補檔）不在這五步裡：那題要等 Alan 提供檔案，隨時可以插入。
